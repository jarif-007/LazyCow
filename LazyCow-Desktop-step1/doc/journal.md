## 2026-10-09 — feat(renderer): secured shortcuts + per-action safety override + mandatory Test Hotkey
- **Issue:** Three coupled problems. (1) The old `showDangerWarnings` boolean conflated two different concepts — a shortcut's *default* secured state, and the user's per-action opinion about which actions are actually dangerous. (2) There was no way for a user to say "this `open_file` is fine" or "this `run_script` is safe" — classification was hardcoded per action type. (3) Test Hotkey (added in the electron commit) needed a UI surface and a Save gate, plus `useHotkeyRecorder` was saving shifted characters (`e.key`) that `globalShortcut.register` silently rejects on UK/Bengali layouts.
- **Solution:** Replaced `showDangerWarnings` with two independent controls. Per-shortcut `secured` boolean on `SavedShortcut` (persisted + synced via `syncHotkeys`) is the runtime gate. Per-action `safetyOverride: 'dangerous' | 'safe'` on `ActionItem` lets the user lock a label; `getActionLabel(action)` returns the override if present, otherwise the computed classification from `isDangerousAction`. `hasDangerousActions(actions)` is the single source of truth for "should a new shortcut default to secured". New `src/utils/security.ts` handles migrations: `migrateShortcutsSecured` (idempotent — runs on Library mount, computes `secured` for any shortcut without one), `readSecuredShortcutsDefault` (falls back to legacy `showDangerWarnings` key, then `true`), `readSecuredDoublePressSeconds` (5–30, default 5). `Settings.tsx` silently migrates `showDangerWarnings` → `securedShortcutsEnabled` on load and deletes the old key. `ConfirmSecuredModal` (new) is an interactive per-action review — filter All/Dangerous/Safe, inline label dropdown per row, and an "all-safe → offer to turn off Secured" prompt. `ComboBuilder` rewritten from `onApply`/`onError` to controlled `value`/`onChange` — modifier toggle chips (Ctrl/Alt/Shift/Win), grouped key dropdown (Letters/Number keys/Function keys/Symbols/Navigation/Special; F1–F24, punctuation, nav keys), live preview pill — so the recorder and the manual picker share one source of truth (`recordedCombo`). ## 2026-10-11 — fix(electron): pre-snapshot + URL title matching for window layout

  1. **Race between the snapshot and the action loop.** The in-script pre-snapshot ran ~400ms after PowerShell started — by which point the shortcut's own browser windows were already on screen. So the engine classified shortcut-opened windows as "old" and refused to place them.

  3. **No URL disambiguation.** Two Chrome windows from the same shortcut share a process name AND a `ProcessStartTime` (Chrome reuses its main process). The engine had no way to tell google.com's window from youtube.com's window.
- **Solution:**
  - **Node-side pre-snapshot.** New `snapshotHandles()` in `windowLayout.ts` runs a small PowerShell `-EncodedCommand` script that returns every visible HWND. `runShortcutActions` awaits it BEFORE firing the action loop, and passes the resulting `Set<string>` through `arrangeWindows(placements, budget, preExistingHandles, signal)` → `buildScript(placements, budget, existingHandlesCsv)`.   - **UI notice updated.** The multi-URL banner in `WindowLayoutPanel` now correctly states Firefox is not supported for multi-URL layouts. ## 2026-10-15 — fix(storage): mirror shortcuts to disk — survives hard kills
- **Issue:** Chromium's `localStorage` writes are asynchronous — they're batched and flushed to disk on Chromium's own schedule, typically within a few seconds. On a **hard kill** (Ctrl+C in dev, where `vite-plugin-electron` force-kills the Electron child; `taskkill /f`; power loss within the flush window), anything not yet flushed is lost. Reproduced twice in one session with cold-cache timing: create shortcut → Ctrl+C immediately → restart → gone; create → wait 3 seconds → Ctrl+C → survives. The earlier `flushStorageData()`-before-`app.exit(0)` fix (feb8473) couldn't close this because no shutdown hook runs during a hard kill. Root cause: `localStorage` is a browser cache, not a durable database, and we were treating it as the primary storage for user-authored data.
- **Solution:** Mirror every shortcut write to a synchronous disk file, and restore from it on startup when `localStorage` is empty.
  1. New `src/utils/shortcutStorage.ts` — `persistShortcuts(list)` writes to both `localStorage` and (fire-and-forget) `window.electronAPI.writeShortcutsToDisk(list)`. `readShortcuts()` reads from `localStorage`. `recoverShortcutsFromDiskIfEmpty()` runs on Library mount; if `localStorage` is empty but the disk file has data, it syncs the disk data back into `localStorage` and returns it.
  2. New `electron/main.ts` IPC handlers: `read-shortcuts-from-disk` (returns `{ ok, data }`; empty array on missing/corrupt file) and `write-shortcuts-to-disk` (`fs.writeFileSync` to `userData/shortcuts.json`, pretty-printed, errors logged not thrown). Synchronous write on the main process — cannot lose data on a kill.
  3. `electron/preload.ts` + `electron/electron-env.d.ts` — bridge the two handlers.
  4. Six call sites swapped from `localStorage.setItem` to `persistShortcuts`: `Library.tsx` (`refreshShortcuts` migration write, `confirmDelete`, `handleRenameSave`, `handleDuplicate`, `handleToggleSecured`, `ConfirmSecuredModal.onConfirm`) and `Builder.tsx` (`handleSave`). Plus a new mount-time recovery effect in `Library.tsx` that calls `recoverShortcutsFromDiskIfEmpty` before `refreshShortcuts` runs.
